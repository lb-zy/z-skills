# Skill 需求契约

以经用户确认的 Skill 需求契约作为实现和验收的唯一语义基线。本 Guide 负责语义决策与契约确认；将资源规划、编辑和结构验证交给系统 `$skill-creator`。

## 决策权

按仓库规范推断路径、命名和平台必需文件等机械信息。把会改变 Skill 结果、行为、范围或验收的语义决定交给用户。用维护源码证明现有 Skill 的当前行为；把仓库规划和 Agent 生成的示例标为候选。只有介绍页或搜索摘要时标明尚未验证。

需求契约至少包含：

- 主要结果，代表性请求、期望输出与不应触发的请求；
- 必要输入、默认行为、输出与能力边界；
- 权限、副作用、停止条件，以及与现有 Skills 的复用、升级、分工、组合、替代或重叠关系；
- 维护来源、修改范围、执行方式和检查方法；
- 完成标准和证据。

首次请求只启动契约形成阶段，确认前保持只读。即使请求看似完整，也展示完整契约并等待明确确认；“直接做”或“你决定”可以减少提问，但不代替确认。确认同时授权按契约修改目标 Skill 的维护源码；安装、提交、发布或超出契约的操作仍需另行授权。

## 形成契约

1. 调查当前请求、对话、维护源码和相关规范，区分有证据的机械信息与待确认的语义决定。完成时，维护来源和现有行为已有依据，全部语义缺口均已识别。
2. 只为会改变 Skill 的缺口或更优方案提问。每次询问一个影响最大的决定，先给出推荐及其具体结果；需要取舍时列出不超过三个实质不同的选项。用户不理解时改用示例；发现职责重叠时展示关系选择。持续到没有待决策项。
3. 用代表性正例、范围边界、相近反例和权限边界场景，逐一走查默认行为、预期输出、停止位置和副作用。出现语义缺口时返回上一步；每个场景的结果都唯一明确后再继续。
4. 展示完整需求契约并明确请求确认。局部决定只记录为契约内容；只有用户看到完整契约后给出的明确确认才通过确认。用户修订语义内容时更新契约并重新请求确认。

## 交给 Creator

确认后立即加载系统 `$skill-creator`，把需求契约作为语义事实来源交给它执行，并让 Creator 决定资源规划、编辑和结构验证。新证据会改变契约时，回到契约形成阶段并在重新确认后继续；依赖不可用时报告阻碍并停止。

## 按契约验收

实现后把每项契约对应到行为证据。实际执行能够运行的代表性正例、边界、相近反例和权限场景；不能执行时记录具体限制。修正契约范围内的不一致并重新验证；修正需要改变契约时，回到契约形成阶段。

每项契约都有通过证据或不可执行限制，且契约范围内可解决的不一致均已修正并重新验证后，验收完成。报告实现结果、证据和剩余限制。
