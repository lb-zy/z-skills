# 建立领域模型

本 Skill 提供建立和维护领域含义及其相互关系的方法，不只是维护术语表，也不替用户作产品、架构或技术决定。模型形成和模型写入分别服从当前请求与文件修改授权，Skill 调用本身不扩大任何一项。

开始建模前综合完整对话，确认主要请求和本次需要解决的领域问题。目标、范围或关键使用情形仍有会改变模型的歧义时，由 Agent 应用 `z-clarify`；共同理解获用户确认前不建立正式模型或修改领域文档。

## 选择上下文

1. 存在 `CONTEXT-MAP.md` 时先确定当前术语属于哪个上下文；否则读取根 `CONTEXT.md`。
2. 检查已有概念、关系、不变量、禁用同义词和相关代码。只有风险或冲突需要时才扩展代码调查范围。
3. 没有领域文档时，在第一个模型决定确认且已有修改授权后按需创建根 `CONTEXT.md`；不要预先搭建空结构。

## 建立模型

- 发现用户用词与词汇表冲突时立即指出。
- 对模糊词提出一个推荐的规范名称，并说明概念的身份和边界。
- 用具体场景检验概念之间的关系、数量、归属、状态变化、领域事件和不变量，例如“一位客户能否拥有多个账户”。
- 区分业务上下文中的语言边界与软件模块边界；前者在本方法中澄清，后者建议 Agent 应用 `z-architecture`。
- 一次解决一个会改变模型的问题；产品资格、权限、价格或失败政策不明确时，建议 Agent 应用 `z-product`。
- 按需核对代码与现有行为；发现模型、代码和用户陈述冲突时呈现证据，不擅自选择哪一方为准。
- 模型不包含数据库、类名、接口或实现步骤。

## 记录与返回

- 只读任务在对话中给出建议模型，不修改项目文件。
- 已有修改授权时，把确认后的概念、关系、生命周期、不变量和上下文归属更新到对应 `CONTEXT.md` 或 `CONTEXT-MAP.md`，并列出应避免的同义词。
- 产品规则、系统边界和实现方式分别建议 Agent 应用 `z-product`、`z-architecture` 和 `z-tech`。
- ADR 由 Agent 在应用架构或技术设计方法时按 [`../_shared/decision-recording.md`](../_shared/decision-recording.md) 判断和记录；领域建模不充当通用决定记录器。

概念及其关系在适用上下文中一致、关键场景与不变量能够同时成立、必要记录已更新或建议已交付后结束。Agent 将模型结果整合到当前任务。
