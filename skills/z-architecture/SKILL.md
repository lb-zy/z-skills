# 架构设计

本 Skill 提供确定长期边界与责任的架构方法，不提前选择表结构、队列、框架或逐文件实现方式。它只覆盖当前架构问题，形成的决定由 Agent 整合到整体任务；不扩大文件修改、实施或发布授权。

开始设计前综合完整对话，确认主要请求、必须保持的结果和本次架构边界。目标、范围或完成标准仍有关键歧义时，由 Agent 应用 `z-clarify`；共同理解获用户确认前不形成正式架构决定。

## 建立事实

1. 读取相关代码、调用链、领域词汇、ADR、部署约束和既有边界。
2. 写清当前架构问题、必须保持的行为、团队与运行约束，以及这次不解决的内容。
3. 产品规则不明确时，建议 Agent 应用 `z-product`；只是当前任务的实现细节时，建议应用 `z-tech`。
4. 需要判断模块深度、接口或接缝时读取 [`../_shared/codebase-design.md`](../_shared/codebase-design.md)。

## 比较真实方案

提出二到三个能在当前约束下实施的方案，至少比较：

- 模块边界与每项事实的唯一所有者；
- 允许的依赖方向和重要接口；
- 跨边界交互中的成功、失败和恢复责任；
- 第三方能力如何隔离；
- 迁移成本、组织负担和可逆性；
- 哪些未来证据会触发演进。

不要默认微服务、模块化单体或新抽象。只有独立发布、合规隔离、显著扩缩容差异、独立团队等真实证据支持时才拆服务。

## 形成决定

明确推荐方案、关键边界、数据所有权、依赖方向、接口语义、失败责任和演进触发器。接口说明意图、输入输出、约束和错误，不在架构层决定进程内调用、消息队列、事务或 outbox。

只有决定难逆、原因无法从代码看出且经过真实取舍时，读取 [`../_shared/decision-recording.md`](../_shared/decision-recording.md)，由 Agent 在已有修改授权时记录 ADR。结束时列出被拒方案及原因、仍需 `z-tech` 解决的问题和对现有系统的迁移边界；不编写正式代码。
