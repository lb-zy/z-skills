# 产品设计

本 Skill 提供把事实、假设和产品取舍分开并形成一致规则的方法，而不是通用 PRD。它只覆盖当前产品问题，已确认规则由 Agent 整合到整体任务；不扩大文件修改、实施或发布授权。

开始设计前综合完整对话，确认主要请求、预期结果和本 Skill 要决定的产品问题。目标、范围或验收依据仍有关键歧义时，由 Agent 应用 `z-clarify`；共同理解获用户确认前不形成正式产品规则或修改文档。

## 建立规则范围

1. 读取已有需求、产品承诺、领域词汇、研究结论和代码中可验证的现状。
2. 写清目标用户、要解决的问题、成功结果、包含范围和排除项。
3. 建立与当前需求相称的规则覆盖：适用对象、资格、触发条件、结果、失败、重试、撤销、时间边界、权限和组合情况。
4. 外部法规、渠道合同或市场事实建议 Agent 应用 `z-research`；术语冲突建议应用 `z-model-domain`。

## 解决取舍

每个会改变产品结果的未决项：

1. 给出两个或多个真实可行方案；
2. 说明对用户、业务和后续工作的差异；
3. 给出明确推荐和理由；
4. 用具体正常、边界和失败场景说明；
5. 一次只请用户确认一个相互依赖的决定。

例如退款规则不能只写“购买后七天可退”，还应明确期限从何时起算、部分使用如何处理、退款是否停止续费以及权益何时失效。不要用惯例替代尚未核实的事实。

## 一致性检查

- 每条规则都有适用对象、触发和可观察结果。
- 失败、重复、取消、到期和权限变化不会与成功规则矛盾。
- 组合规则在同一具体场景中能够同时成立。
- 未确认内容明确标为假设或开放问题，不能伪装为决定。

## 输出与结束

产物只保留目标、对象、决定原则、场景规则、排除项、依据或假设、待核实事实和确认状态。界面呈现、系统边界和实现方式分别建议 Agent 应用 `z-ui-design`、`z-architecture` 和 `z-tech`。

关键产品取舍均已确认、交叉场景一致且剩余问题不阻碍下一步时结束。已有项目修改授权时写回当前设计或规格来源；只读任务在对话中交付确认结果，不修改文件。
