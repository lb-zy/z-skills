# 形成与演化 Skills

本 Skill 提供从真实问题证据到候选方法、行为验证和正式采用的完整演化方法。Agent 负责理解案例、判断边界、实施修改和整合结果；本 Skill 不扩大当前源码、运行安装、外部系统、提交或发布授权。

## 确认本次目标与影响

1. 结合完整对话确认用户要形成新 Skill、改进现有 Skill、合并重叠能力、删除失效能力，还是只分析候选。
2. 明确允许读取的案例、允许修改的源码位置、是否包含评测与设计文档，以及是否要求部署到运行目录。
3. 将讨论、候选形成、源码采用和运行部署视为不同影响。只执行当前请求明确覆盖的部分。
4. 一次演化聚焦一个可观察问题；结构性变化确实牵涉多个 Skills 时，再扩大到必要集合。

## 从真实案例建立证据

1. 收集原始用户需求、可用上下文、Agent 实际行动、使用过的方法与工具、产生的结果、验证证据和用户反馈。
2. 同时选择成功案例、失败或遗漏案例、相近但不应使用该方法的反例，以及需要与其他能力组合的案例。
3. 无法取得原始来源时明确证据限制，不根据摘要补造过程。单个成功案例通常只形成候选，除非方法本身已有可靠专业依据和可验证边界。
4. 把问题写成可观察差异，例如误选、漏选、专业步骤遗漏、结果质量不足、组合冲突、过程不可感知或上下文成本过高。

## 提炼专业方法

1. 找出案例中反复出现、对结果有因果价值的专业判断、步骤、证据和质量标准。
2. 删除属于 Agent 原生能力的内容：理解当前发言、选择 Skill、决定下一步、调用工具、读取反馈、维持总体目标和整合最终结果。
3. 检查现有 Skills 与共享资料，优先修正或复用真实重叠能力；只有新边界能够独立说明、复用和验证时才新增 Skill。
4. 为候选确定名称、结果、适用条件、反例、专业方法、质量标准、边界和组合提示。范围应清楚且有足够深度，不追求形式上的最小粒度。
5. 不声明永久的主导、辅助、场景或编排类型。Skill 在具体任务中的作用由 Agent 决定。

## 实现候选

在已有源码修改授权时：

1. 先修改唯一源码中的 `SKILL.md`、调用元数据和必要资源，不先改运行副本。
2. 使用当前平台规范校验目录、frontmatter、名称、描述和元数据；描述应让 Agent 能准确发现正例并排除相近反例。
3. 只保留执行该专业方法真正需要的正文、脚本、参考资料或模板，删除重复规则和已经失效的内容。
4. 更新被变更直接影响的设计说明、索引和评测案例，保持每项事实只有一个权威来源。
5. 保留用户已有改动，不顺手改造无关 Skills。

## 验证候选

1. 执行结构检查，确认名称、目录、frontmatter、元数据、链接和引用一致。
2. 使用至少两个正例、两个相近反例、一个组合案例、一个授权边界案例和一个结果质量案例进行前向验证。
3. 测试 Agent 只接收原始请求与必要环境，不提前看到预期 Skill 路径或判定答案。
4. 比较修改前后的选择准确性、专业结果、组合表现、过程可见性、授权边界和上下文成本。
5. 未达到成功标准时保留为候选或继续调整，不把结构校验通过表述为方法已经有效。

## 采用、部署与继续演化

候选在代表性案例中达到成功标准，且用户已授权修改源码时，才作为正式 Skill 采用。报告证据、实际变化、验证结果和剩余盲区。

运行目录部署是独立动作。只有用户明确要求部署到指定目标时，才保留可恢复副本、更新运行文件、核对逐文件一致性并确认 Skill 可被发现；源码采用不自动获得这项授权。

后续真实使用继续提供演化证据。重复、边界混乱、长期未带来收益或已被其他方法覆盖的 Skill，应比较改进、合并与删除，而不是只增加新层或新名称。
