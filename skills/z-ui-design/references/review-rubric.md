# UI 评审标准

评审目标是找出妨碍用户完成任务的问题，并给出可复查的证据；不是罗列个人审美偏好。

## 取证

- 在确认的视口、内容和状态下检查真实界面。记录页面或区域、状态、视口和可观察现象。
- 截图、测量值、可复现步骤或工具结果能决定结论时，必须附上。
- 代码只能解释原因，不能代替对已渲染界面的检查。
- 无法进入的状态标为未验证，不推断为通过或失败。

## 评审顺序

1. 核心任务是否可发现、可完成、可恢复。
2. 信息架构与视觉层级是否支持扫描、比较和决策。
3. 控件、反馈、状态和错误处理是否清楚且一致。
4. 响应式布局、真实内容和极端内容是否稳定。
5. 键盘、可访问名称、语义、对比度和目标尺寸是否可用。
6. 字体、色彩、间距、图标、边框和动效是否形成一致系统。

## 优先级

| 级别 | 判定 |
| --- | --- |
| P0 | 导致数据损失、安全风险，或核心任务对多数用户完全不可用。 |
| P1 | 阻断核心任务、关键状态不可理解，或存在严重无障碍障碍。 |
| P2 | 任务仍可完成，但明显增加错误、时间或认知负担。 |
| P3 | 局部一致性或完成度问题，对任务影响有限。 |

不要按视觉显眼程度定级。相同问题系统性出现时合并报告，并说明影响范围。

## 单条发现格式

- **问题**：一句话描述可观察的问题。
- **证据**：位置、状态、视口和复现事实。
- **影响**：受影响的用户与任务后果。
- **优先级**：P0-P3 及判定依据。
- **建议**：解决结果和必要约束，不越权决定业务规则。
- **验证**：修正后可重复执行的检查。

先给出按优先级排序的发现，再简述已检查范围、未验证项和跨页面模式。没有发现时明确说明，并保留测试覆盖缺口。
