# 软件设计文档体系

本目录提供一套可复用、可裁剪、可验证的软件设计文档模板。它们用于把产品意图转换为能实现、能评审、能验收和能运维的设计，不规定某种技术栈或强制开发流程。

## 核心原则

1. **记录决定，不复制实现**：说明上下文、选项、取舍、后果和验证方式。可从代码、配置或生成物准确得到的细节只建链接。
2. **每个关键声明都可验证**：不使用“高性能”、“高可用”等无法验收的形容词，改为指标、阈值、环境、时间窗口和证据。
3. **一个事实只有一个权威来源**：例如 HTTP 契约以版本化 OpenAPI 文件为准，表结构以迁移脚本为准，设计令牌以令牌源文件为准。
4. **保持可追踪**：用稳定编号连接目标、用例、质量需求、模块、接口、数据、风险、决策和验证证据。
5. **按风险裁剪**：低风险改动不需要填满所有模板；一旦涉及数据不可逆变更、权限、外部契约或可用性承诺，必须补齐相关设计。
6. **文档与实现同步演进**：文档和代码在同一版本库评审；决定变更时同步更新设计、契约、ADR 和验证证据。

| [02 架构设计](./02-architecture.md) | 系统视图、模块职责、接缝和运行方式 | 新系统、跨模块改动或关键质量受影响 |

## 使用方法

### 1. 裁剪

先根据改动范围和风险选择文档。复制所需模板到项目中，删除不适用的章节并简短记录原因，不保留空洞标题。

| 风险 | 典型特征 | 最小文档 |
|---|---|---|
| 低 | 局部、可快速回退、无契约或数据变更 | 01 的精简版 + 09 |
| 中 | 跨模块、新接口、新页面、可观察的性能影响 | 01、02、相关专项文档 + 09 |
| 高 | 不可逆数据变更、资金/隐私/权限、公共契约、高可用承诺 | 所有相关专项文档、ADR、威胁与故障演练证据 |

### 2. 统一元数据

每份项目文档的开头保留以下信息：

| 字段 | 要求 |
|---|---|
| 状态 | `草案` / `评审中` / `已批准` / `已取代` |
| 负责人 | 对内容正确性和更新负责的唯一角色或个人 |
| 评审人 | 产品、设计、开发、测试、安全、运维中实际受影响的角色 |
| 最后更新 | ISO 8601 日期，例如 `2026-07-29` |
| 范围/版本 | 适用的产品、发布版本或里程碑 |
| 关联项 | 需求、问题、契约、原型、ADR、代码和证据链接 |

### 3. 建立追踪编号

可按项目需求调整前缀，但一旦引用就不重排：

| 前缀 | 含义 | 示例 |
|---|---|---|
| `G` | 目标/非目标 | `G-03` |
| `UC` | 用例或业务场景 | `UC-07` |
| `QR` | 质量需求 | `QR-04` |
| `MOD` | 模块 | `MOD-ORDER` |
| `IF` | 接口 | `IF-HTTP-02` |
| `DATA` | 数据集或实体 | `DATA-ACCOUNT` |
| `RISK` | 风险 | `RISK-05` |
| `ADR` | 架构决策 | `ADR-0012` |
| `TEST` | 验证项 | `TEST-PERF-03` |
| `SLI` / `SLO` | 可靠性指标/目标 | `SLO-API-01` |

### 4. 评审和变更

1. 作者标注事实、假设、已决定项和待决定项。
2. 评审人只接受有完成证据的结论；无法当前验证的项目进入风险表。
3. 重大决定写入 ADR，其他文档只引用 ADR，不重复论证。
4. 实现中出现新事实时，先修正设计或显式记录偏差，不让文档静默过期。

## 进入实现的最低门槛

- 范围、非目标、关键用例和术语已确认。
- 关键质量需求有度量方法和目标值。
- 模块职责、接口、不变式、数据所有权和故障方式已明确。
- 外部契约已版本化，兼容性和废弃策略已确认。
- 数据迁移、回滚、保留、备份和恢复方案与数据风险匹配。
- 权限、隐私、威胁、依赖故障和降级行为已覆盖。
- 每个关键需求至少对应一个可执行验证项。
- 所有高风险未决项都有负责人、决策日期和临时措施。

## 参考基线

以下页面已于 2026-07-29 核对。它们提供思考框架和检查基线，不代表本文档体系自动满足法律、合规或认证要求。项目应锁定实际采用的版本，不在未评审时自动跟随 `latest`。

- [ISO/IEC/IEEE 42010:2022](https://www.iso.org/standard/74393.html)：架构描述中的利益相关者、关注点和视图。
- [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html)：系统与软件产品质量模型。
- [C4 model](https://c4model.com/)：系统上下文、容器、模块和代码级视图的渐进表达。
- [arc42](https://docs.arc42.org/home/)：可裁剪的架构文档结构与示例。
- [Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)：ADR 的上下文、决定、状态和后果。
- [OpenAPI Specification 3.2.0](https://spec.openapis.org/oas/latest.html)：HTTP 接口的机器可读契约；项目必须锁定具体版本。
- [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)：HTTP API 的 Problem Details 错误格式，已取代 RFC 7807。
- [OWASP ASVS 5.0.0](https://owasp.org/www-project-application-security-verification-standard/)：Web 应用技术安全控制和验证要求。
- [OWASP API Security Top 10:2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/)：API 主要风险检查基线。
- [WCAG 2.2](https://www.w3.org/TR/WCAG22/)：可感知、可操作、可理解和健壮的 Web 无障碍要求。
- [ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/)：复杂 Web 控件的语义、键盘交互和焦点模式。
- [Core Web Vitals](https://web.dev/articles/vitals)：加载、交互响应和视觉稳定性的用户体验指标。
- [Google SRE: Implementing SLOs](https://sre.google/workbook/implementing-slos/)：SLI、SLO 和误差预算的实践。
- [OpenTelemetry Observability Primer](https://opentelemetry.io/docs/concepts/observability-primer/)：指标、日志和分布式追踪的可观测性基础。
- [The Twelve-Factor App](https://12factor.net/)：配置、依赖、构建/发布/运行分离和无状态进程等部署原则。
