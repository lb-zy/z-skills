# 澄清需求

本 Skill 提供聚焦关键歧义的澄清方法，不把用户拖入固定访谈或完整需求填表。Agent 始终是执行者；本方法不扩大当前目标、文件修改或后续实施授权。单独提出想法、反馈、抱怨、背景信息、问题或未来意图，不等于要求启动澄清或后续开发。

## 工作方法

1. 读取完整对话、现有需求、代码、规格、设计、词汇表和 ADR，不只解释最近一句。
2. 区分当前主要请求，以及最新发言是新任务、继续、补充事实、问题、反对、反馈、确认还是明确 Skill 调用；非任务性发言只更新理解，不开启新的工作路线。
3. 复述已知的目标结果、范围与排除项、关键行为、约束和验收依据，明确哪些缺口确实会改变结果。
4. 将缺口按依赖排序，先解决会改变其他决定的问题。
5. 一次只问一个问题；说明为什么现在需要决定，给出推荐答案和至少一个具体场景。
6. 用户回答后先在当前对话中形成稳定结论；只有当前任务已经授权修改对应需求、设计或规格时才写入其事实来源，再决定下一个问题。
7. 事实能从环境或资料取得时自行核对，不把搜索工作交给用户。

未知问题按性质分流：

- 代码库事实：直接检查代码、配置和文档；
- 外部客观事实：由 Agent 应用 `z-research`；
- 必须实际操作或观看：由 Agent 应用 `z-prototype`；
- 领域术语冲突：由 Agent 应用 `z-model-domain`；
- 产品、界面、架构或技术取舍：由 Agent 选择相应 Skill，不在澄清中代做。

## 确认点

只有真实取舍交给用户。每题推荐必须结合项目事实，例如：“推荐首版只支持月付，因为当前目标是验证购买闭环；年付会增加定价和续费规则。是否采用？”不要询问函数名、文件位置或测试框架等普通实现细节。

## 结束条件

以下内容足够清楚时，先集中呈现一份紧凑的共同理解并请用户确认：

- 能清楚复述目标结果；
- 当前范围和排除项足以确定；
- 关键行为有具体例子或验收依据；
- 重要约束与风险已知；
- 没有阻碍下一步的用户决定；
- 需要证据的问题已经进入研究或原型岔路。

用户确认共同理解后，输出仍保留但不阻塞的问题，并把控制权交回 Agent。原目标和授权已经覆盖下一项工作时，Agent 可以继续选择适用 Skill；否则只交付共同理解和下一步建议。用户确认前不得开始产品、界面、架构或技术设计，不得创建正式文档、修改项目或实施要求。不要为了“完整”继续追问，也不要把澄清回答视为扩大修改授权。
