# 疑难 Bug 诊断与修复

反馈先于假设。没有能观察精确症状的信号时，不凭代码阅读猜根因。

## 核对修改授权

进入本 Skill 或补充症状不自动授权修复。首次修改项目成果前，必须存在明确修复要求、包含修复的交付任务或仍有效的持续修改授权；否则只读诊断并报告证据与建议，不进入修复闭环。

## 建立稳定反馈

1. 读取用户症状、环境、版本、日志、近期变化、词汇表、ADR 和相关代码。
2. 建立能够反复显示问题是否存在的测试、命令、请求重放、日志查询、指标或性能基准。
3. 实际运行并确认它驱动真实故障路径、捕获用户描述的症状，而不是附近的另一个失败。
4. 缩短耗时、收紧断言、固定时间与随机性；间歇问题通过循环、并发、压力或窗口控制提高复现率。

需要读取线上信息、增加生产探针或操作真实数据时，先说明范围、敏感数据和清理方式并设置确认点。无法建立反馈时列出已尝试方法以及所需环境、捕获物或权限，然后停止猜测；此时不得加载或应用 `z-tdd`、`z-code-review`，因为尚未进入修复闭环。

## 缩小与证伪

1. 一次删除一个输入、调用者、配置或步骤，保留仍能触发症状的最小场景。
2. 根据现有证据提出足够数量的可证伪假设并排序；每项写明若成立应观察到什么。
3. 一次只改变一个变量，优先调试器或边界探针，不使用“记录一切再搜索”。
4. 临时日志使用唯一前缀，只记录必要标识或哈希，不记录完整支付载荷、密钥或个人数据。
5. 性能问题先固定基线，再使用剖析、查询计划、版本或数据二分；不先做凭感觉优化。

## 修复闭环

只有稳定反馈已经建立且修改授权有效，才进入本节并由 Agent 按需应用其他 Skills。

在能反映真实故障的接缝，由 Agent 应用 `z-tdd` 建立失败回归测试；没有正确接缝时明确记录这一架构限制。完成最小根因修复，不顺手扩张为架构重写。

随后必须：

- 运行回归测试并重跑原始未缩小场景；
- 执行匹配风险的相关测试、静态、构建或性能检查；
- 由 Agent 应用 `z-code-review` 执行两轴评审并修复问题；
- 删除临时探针与一次性调试物；
- 报告根因证据、修复、验证结果和盲区。

若根因暴露长期架构改善，先完成当前修复，再把改善作为新的候选要求记录。原请求没有覆盖长期改善时只报告建议；已有目标和授权覆盖时，Agent 可继续应用 `z-improve`、`z-architecture` 或匹配方法。重大迁移需要技术设计时，可由 Agent 应用 `z-tech`，再将决定整合回修复工作。
