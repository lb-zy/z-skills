# 代码评审

评审只读取与验证；修复由具备相应授权的 Agent 或原作者另行完成。

## 固定目标与依据

1. 确定比较点和完整改动范围。用户已指定提交、分支或基准时遵从；否则根据工作区与分支状态选择安全基准，无法可靠推断时询问。
2. 读取适用的用户要求、确认规格、交付任务、完成标准和用户提供或确认的目标参照。要求轴只根据这些依据判断；没有依据或主观目标缺少必要参照时，记录验证盲区，不能标为通过。Agent 自选的页面一致性、内部阈值或代理指标只能证明局部事实，不能替代用户目标。
3. 读取项目规范、完整差异、必要上下文、调用者和相关测试；区分本次改动、既有问题和基线失败。
4. 按风险决定执行方式：低风险可在当前上下文顺序评审；高风险优先使用一个或两个独立上下文。独立性不可用时不省略任一轴。

## 两条独立轴

**要求符合度**检查：

- 要求、规则或完成标准是否缺失、部分实现或行为错误；
- 是否实现了规格之外的功能、扩大数据范围或擅自改变体验；
- 表面存在的功能是否在真实路径上满足要求。

**工程质量**检查：

- 正确性、边界状态、错误处理和回归；
- 安全、权限、隐私、秘密与外部输入；
- 并发、幂等、事务、双写、迁移和恢复；
- 性能、资源、兼容性和可观测性；
- 测试保护、项目规范、复杂度和可维护性。

运行与改动相关且保持源代码不变的测试、类型、静态或构建检查，记录命令、结果和已有基线失败。

## 报告门槛

只报告同时满足以下条件的问题：由本次改动引入、影响具体、能够从代码或运行证据证明、作者会采取行动。删除推测、风格偏好、重复发现和无关既有问题。

发现按 P0 到 P3 排序，每项包含所属轴、精确改动行、触发场景、实际影响和最小修正方向。先列发现，再给简短总结；不要用一条轴的通过掩盖另一条轴的问题。

没有发现时明确写“未发现问题”，同时说明评审范围、执行过的检查、缺失规格和验证盲区。不得为了填充报告编造问题，也不得直接修复代码。
